# AGENTS.md — shared rules for Claude Code, Muse Code and Claude

All agents read this file first. `docs/PRD.md` is the source of truth for scope; `docs/SPIKE.md` is the current task list. If code and PRD disagree, flag it instead of silently picking one.

## Project
Native iOS app, Swift + SwiftUI + ARKit. Target device: iPhone 15 Pro (LiDAR, A17 Pro, Action Button), borrowed, available ~2–3 h/day. Developer Mac: Nils's. Indoor only.

## Division of labour
| Who | Owns |
|---|---|
| **Claude Code / Claude** | Main Swift codebase: ARKit, Vision hand pose, guidance controller, Model API client, architecture, code review, docs |
| **Muse Code** | Scoped tasks only: one function, one bug, one test, one script. Keeps the repo honest that Meta's coding agent was used |
| **Nils** | Runs builds on the iPhone, tests, reports logs and numbers, decides scope |

Muse Code works on a branch per task (`muse/<task>`); Claude reviews before merge.

## Current find-and-grab contract (v9.1, with the v9.2 additions, 2026-10-31)
Nils, after the v8 run: "having the pre set up is a good idea, but the whole process is a piece of shit user experience, and the voice instruction is crumbled." Decisions: keep the safety base, redo the flow and the voice.
- **Reach:** measured once (long press, index fingertip held out comfortably) and saved across launches, with the hand length (wrist to index tip); re-measure only on request. **Distance never stops guidance** (Nils, 2026-10-31: "I don't care how far the object is, it must guide"); the reach scales thresholds and decides staged waypoints only.
- **Controls:** one screen. Tap = start listening / stop (ends a room scan early; it also ends by itself). Double tap = "Is this it?" (since 2026-11-01; was "I have it"): it runs a check and answers. Long press = measure reach. VoiceOver: activate = double tap, magic tap = tap, named actions for the rest.
- **Speech engine (branch `muse-voice`, 2026-11-01, Nils: "open a new branch for muse voice, i want to test first"):** each listen streams the microphone to Muse Voice Transcribe realtime (keywords = room names + target, languageBias English) and to Apple on-device at the same time; Muse decides when the user finished (`docs/STT_EXPERIMENT.md` stop rule) and its text is used, Apple is the fallback when Muse fails; both go to the find log (`stt`). A waveform button switches Muse / Apple for A/B. Cost about $0.0003 per listen. Not merged until Nils has tested it on the phone. The open mic during guidance (spoken "Is this it?") is not built yet.
- **Spark replies (Nils, 2026-11-01):** no word caps; every prompt asks for the simplest reply a blind person can act on at once (`MuseAgent.simplest`, agent instructions).
- **Audio after a listen (T22, Nils: "the voice is easily cut by the beep"):** every listen waits until the output is back on the loudspeaker (`AudioSessionKeeper.settle`, 0.2-1 s) before the heard beep and the next line; the session category is set only when it differs. Guidance beeps are a quarter volume while the voice speaks.
- **Voice:** one action per line, about 8 words or fewer. Never name on-screen buttons. No disclaimers in speech ("contact is not confirmed" belongs in docs). Only Stop, obstacles and check results interrupt.
- **v9.2 (Nils, 2026-10-31, after the below-8/10 list):** touching things on the way is normal for a blind user; time to the object is the core KPI. Obstacles: no stop and no planned detour by default; one Spark look (numbered marks on a photo) names the things in the map, and the line says the name and the side to pass it ("A bottle is ahead. Go around it on your right."). The side is chosen by geometry (the object's side, else away from it, else fewer things), not by the LLM, because it must be instant. Rolling scan: the map is extended about once a second; a cell joins only when seen in two scans in a row, arm and hand removed. A stalled hand (same direction 4 times) and an empty spot (LiDAR, objects ≥ 3 cm thick) start a hold check, which looks at the spot again (supersedes "a stalled hand gets no check" below). Hand gone ~11 s: "I need to see your hand to guide you." and a short spoken conversation with Spark (≤ 3 turns). Hand on the object 12 s without a pick-up: "It's right below your hand." every 6 s.
- **v9.2 follow-up (Nils, 2026-11-01, after reviews by Muse Spark and GPT):** every 8 s wait is 6 s. Spark verifies every lock, the agent's choice too; a rejected lock is skipped, and after 3 rejections (or a scan with nothing else) the likeliest rejected one is guided to with "I'm not sure this is the X." No Spark answer (network): the lock stands. One Spark look at every lock names the mapped things, flags dangerous ones and finds dangerous things too low for the map (a knife lying flat); dangerous things are always stopped for and gone around (safety is a KPI; touching ordinary things is fine), and if the look fails twice: "I couldn't check for danger. Go slowly." Another thing like the target nearby: a short Spark-led talk asks which one, then guides there (silence keeps the first). No support height: the map keeps every surface, the table too, except where the hand lands (the surface is not guessed). The hand is removed from rolling scans by its shape (finger and palm capsules sized from the measured hand length; the wrist inferred toward the camera when only fingertips are seen), not a 9 cm ball. **Holding it, sure or not (Nils, 2026-11-01):** case 1, the user has it and knows it is the one: they just close the app; nothing asks for "I have it". Case 2, they have something and are not sure: they ask "Is this it?" (double tap now; voice depends on the STT choice, see `docs/STT_EXPERIMENT.md`). Answers: "Yes. That's the X." / "No. The X is still there." (guide again) / "I can't tell. Hold it up to the camera." and one more look 3 s later (outside the automatic budget; once per search; no hand in view then: "I can't see it. Hold it in front of the phone." and 3 s more). If that look still cannot tell, Spark tells the user how to move it into view or what it sees in their hand (colour, shape, size, words on it, whether it looks like the X), then "Double tap to check again." (Nils: "It may be the X." is not a responsible answer.) At most 2 descriptions per search; after that an unsure check, or a double tap after one, says "The camera can't tell. Feel it, or close the app if it's right." with no API call. A check that cannot tell never takes the user's word any more (`user_confirmed` is obsolete). A hand that leaves the object after that is guided again. Tap vs double tap: a single tap waits for the double tap to fail (SwiftUI), so they do not overlap.
- **Room map and look-alikes (Nils, 2026-11-01, after the v9.2 device run):** the room scan ends by itself after a full circle with at least 6 views listed, or at 12 views (no "Tap when done"). At launch the app tries up to 30 s to match the saved map and says "Saved room found." or "I couldn't match the saved room. Say scan the room to save it again."; a tap to search before that starts fresh tracking at once. **What the map holds and how it is used without an ARKit match (Nils: "let the LLM read the map and infer"):** the room scan saves names, positions (saved frame), what each object stands on and fixed landmarks (desk, shelf, lamp); no photos. Relations ("on the desk, next to the laptop") need no frame and are said when there is no direction yet; Spark's guess for an unmapped thing uses them too ("It might be near the laptop."). Landmark alignment: at the start of each search and on new scan views, one Spark call lists what is in view; 3 saved things that agree within 25 cm, or 2 fixed ones, give the turn and shift to the saved frame (a moved cup is left out), at most 2 per search and 6 per launch; after that the map gives directions as if ARKit had matched. A thing not in view that the room map has: the agent turns the user there (`scan_for`, which says where it was saved) instead of searching the current view again. After each `find_object` the agent gets the photo with every candidate boxed and labelled, and asks about look-alikes by how they look first (colour, see-through, shape, size, what is in them), then by place. A LiDAR shape far wider than the object's photo box (a clear glass: depth goes through it) is dropped and guidance uses the centre only.
- **Spark picks, SAM outlines (Nils, 2026-11-03, after T13-T17: "why do we need so many components to distinguish one thing?"):** `FindModel.sparkFirst`. Each search photo goes to one Spark call (medium) with the user's own words; it points at the one thing they mean (`SparkPick`: want, visible, x, y, what it looks like, how it differs), choosing the nearest when their words do not tell look-alikes apart. SAM is asked for what Spark says it looks like on a crop around the point, then for the target name; the outline holding the point is the target, else a square around the point placed by LiDAR. No yes/no check after it. SAM's name for the target (hold checks too) is the pick's. **Nothing from before is lost (Nils, 2026-11-03, after T18):** every search photo (the lock, each scan view, the agent's `find_object`) is picked by Spark first (`findCandidates`); Spark says not in view or gives no answer: the SAM-first search runs as before (map crop and saved-spot check, tiles, SAM names, Spark's yes/no, rejected list, the agent choosing between several). Spark picks but SAM draws no outline at the point: the full SAM search on a new photo, and its outline within 10 cm of the point is taken; else a square around the point. Commands the parser cannot read go to the agent as before (multi-find, questions, room hints); its `select_target` skips the yes/no for a Spark-picked candidate, and a Spark-picked candidate from its `find_object` is guided to at once, with no more agent turns (T24: 4 more turns, 142 s to the lock). The which-one question, guidance, obstacles and hold checks are unchanged. `sparkFirst = false` turns Spark picks off. **Saved spot in view (T23, Nils: "too slow to find the supplement bottle"):** SAM's crop at the room map's spot runs at the same time as Spark's pick, and what it finds there is taken at once (Spark's yes/no checks it); the pick took 5-9 s and once said "not in view" with the bottle in the photo. **OBSOLETE since T28 (Nils, 2026-11-04: "remove the map spot going first; what is in view, use the view"):** `spotFirst = false`; Spark's pick on the view decides, and the map's spot crop runs only after it says not in view. The saved map's which-one question is asked then too, not before the view (Nils: "when it's at the screen, use the screen").
- **Ask which one, always (Nils, 2026-11-04, after T21: "no matter what, ask what exactly the user wants"):** when the room map holds more than one thing the word fits (two water bottles, or a water bottle and a bottle saved with that alias; entries of one name closer than 25 cm, or of any name closer than 8 cm, are one thing), every search asks before looking, describing each thing, then what it stands on (T22: neighbours too made it 13-19 s; they are said only when nothing else places it): "I remember a black metal water bottle with an AMD logo, on the desk and a white plastic water bottle with a light green lid, on the side table. Which one?" (Nils, 2026-11-04: "I want it to describe, not just say where"). The look comes from the room scan: the same Spark call saves `look` per thing (up to 8 words with its name, colour first, then material, size, words or logo; no extra call); maps saved before have the name only; distance only when nothing is known of the place. The answer is matched by place words, "nearer" / "far", or "first" / "second" (`FindRules.pickSaved`, no API call); words that already tell skip the question; a second try is shorter, by look (else by place); no clear answer takes the nearer one and says so. The choice steers the map hint, the map crop and Spark's pick (its look and place are added to the user's words); a chosen thing not in view starts the scan toward it at once. **Spark leads the talk (Nils, 2026-11-04: "if the system doesn't recognise the difference at first, it can ask the user; Spark is an advanced model, so no need to limit what it says, only time and rate"):** each turn sends Spark the user's words, what the map knows of each option (name, look, what it is on and next to, distance) and the talk so far; Spark writes the question and decides the choice, its words not restricted. Limits: 8 s a call, 4 calls a search (minimal effort, text only); no Spark answer: the app's own question above for that turn. Same-sounding options are asked about too (the T22 "same look" skip is obsolete). The options' words are keywords for the recogniser while it listens for the answer. Without a choice, of two saved things with the name the nearer is meant (`RoomInventory.match/target(near:)`). The look-alike question in view (below) asks too (T25, 2026-11-04: Spark chose the first water bottle at once and never asked): until the user has said which one, here or to the saved question, Spark's choice is not taken; it is asked once more to ask, then the app asks "There is more than one X here. Which one do you want?"; silence still keeps the locked one.
- **What SAM is asked for, and looking again (Nils, 2026-11-02, after T13: "vitamin" found nothing with the jar in view):** SAM only understands names of things it can see. It is asked for, in order: the saved room's name (the user's word plus more, "vitamin" -> "vitamin bottle", or an alias the room scan saved, "supplements"; only when the word fits one saved thing: "bottle" with a water bottle and a vitamin bottle saved stays "bottle"); else Spark's name for the word, asked once per word ever (text only, effort minimal, in parallel with the first SAM call on the user's word) and kept in `Documents/sam_names.json`; else the user's word. When the room map's spot for the object is in the photo, SAM looks at a crop around it first (one call, also for small things); nothing there sends the same photo to the whole-photo path, and after 2 such misses a search uses whole photos only. The scan counts a direction as searched only from within 75 cm of where it was searched: after walking, the same directions are looked at again (a thing hidden behind a bigger one). The saved spot in view but never looked at from here makes the view new; facing it but above or below the view says "Point the phone a little higher." / "lower" (v9.4: a mantel above the chest phone got "Hold still." 3 times and no call). Hold checks ask SAM for the same name as the search. The target's unseen back (behind its visible surface from the lock camera, up to the photo box width deep) is never an obstacle (v9.4: the bottle's own back was called "something ahead"). A saved spot seen clearly (within 2 m, nothing in front) and empty twice in a launch: "I remembered a X on the Y, but it isn't there." and that entry is forgotten (v9.4: a shaker saved as "water bottle"). The agent: after 2 names found nothing in view, the next `find_object` scans for the first name instead (v9.4: 6 names on a view without the bottles). After a landmark alignment, the movable things in that same Spark listing update the map as `seen` (no extra call), as a rolling update: a saved thing whose spot is in that photo, within 3.5 m, with nothing in front of it, but which was seen elsewhere has moved and its old entry goes (`room_map_moved`); saved things out of view or hidden stay. A word that fits several saved things ("bottle": a water bottle and a vitamin bottle) gets no direction to one of them: the app says "I remember a vitamin bottle and a water bottle." and scans (`room_several`).
- **Nothing latches:** a lost hand says "I can't see your hand." at once, then every 10 s while it stays gone; lost tracking says "Hold still." and resumes; a turned or moved body re-bases the direction frame; an object off to the side asks the user to turn, then guides. Obstacles (v9.1): one map from the lock frame (`ObstacleMap.scene`, shared with the simulator), never a live full frame (it held the user's own arm). A move heading into one: "Stop. Something's in the way.", then a way around (another axis, a sideways shift onto the object, back, or up and over); if none is clear, "Go slowly. Something is on your left." and guide on. Nothing ends a search; 20 s without a pick-up says "Let's try again." and guides again. Never more than 8 s of silence while guiding.
- **Phone load (T24, Nils: "some screen lag"):** every 5 s the find log gets `perf` (frames processed per second, mean and longest ms per frame, thermal state, memory free). Thermal serious or critical: bursts off and the rolling map scan every 2 s (`thermal`). **Less load from the start (T26, Nils: "it is because Sightline running so the phone over heat"):** camera and tracking at 30 fps (same resolution; `video` in the log), frames processed at 30 Hz only while guiding, holding or measuring reach and at 10 Hz otherwise, and the screen draws no lighting, shadows or effects. Landmark alignment during a search lists at minimal effort (36 s at medium); the room scan stays at medium.
- **Body scale (v9.1, Nils):** no centimetre threshold is absolute. Arm-sized ones scale by reach / 52 cm, hand-sized ones by hand length / 18 cm, clamped 0.6–1.5 (`BodyScale`). Object and sensor thresholds are not scaled.
- **Pick-up trigger (v9.1, object-centred):** a hand put down and lifted without touching the object must not count. A check needs a contact candidate first (≥ 2 fingertips within a hand-sized 4 cm of the object), then the hand leaving (reach-scaled 10 cm), rising (reach-scaled 5 cm for 0.2 s) or being lost for 1.5 s. One check per event. A stalled hand gets one "Double tap if you have it." and no check.
- **Recording (record only):** each check logs `spot_evidence` and saves a 2 s + 2 s burst at 10 Hz (≤ 5 per search, ≤ 30 per launch). They do not change results.
- **Hold check (back to v7):** the trigger above starts a check at once (Nils, v7: no waiting for a manual check). One photo: 1 SAM + 1 Spark (photo + reference crop), combined by `HoldDecision`. At most 6 automatic checks per search; hold-SAM budget 12. Results: "Got it. You have the X." / "The X is still there." (guide again) / "Not sure. Double tap if you have it."

## Architecture rules
- **Cloud = understand and decide.** Muse Spark and SAM 3.1 via Meta Model API (`https://api.meta.ai/v1`, OpenAI-compatible). Never call them per frame.
- **Device = measure and guide.** ARKit (LiDAR depth, world tracking, RoomPlan), Vision hand pose, local guidance controller. The 30–60 Hz loop must never wait on a network call.
- Muse reads live state only through tool calls (e.g. `get_state()` returning target/hand/obstacle coordinates in ARKit world space, metres).
- SAM masks are projected to 3D with the aligned LiDAR depth map; store the target as a world-space anchor.
- Coordinates: ARKit world space (x right, y up, z toward user, metres). No GPS.

## Cost rules (zero out-of-pocket)
- All usage bills the $150 hackathon Model API credit. **Never subscribe to a paid Muse Code plan.** Muse Code signs in with the Model API key, not browser sign-in.
- Meta requires a card on file to use the credit, so set the Billing **Spend Limit** to $150 or less. Alerts at $50 / $100 / $140.
- **SAM is event-triggered, not 1 Hz:** call it on target lock, when tracking confidence drops, and once before "now grab". Target ≤ 5 calls per guidance session.
- **Downscale images to ~512 px** on the long edge before any upload.
- **Muse Spark effort by job** (Nils, 2026-10-28, from G4): `minimal` for fast-path calls (naming objects, short yes/no checks, spoken replies); `medium` for real reasoning (choosing between several SAM instances, planning) and, since 2026-10-29, for every agent turn (understanding the user matters more than a second of latency). Keep `max_output_tokens` generous — reasoning tokens count toward it. Spark is never on the critical path to the first spoken guidance.
- **Exceptions approved 2026-10-29 (Nils: "全做"), all event-triggered:**
  - Keep-scanning when the object is not in view: ≤ 8 SAM calls per search.
  - Small objects (keys, rings …): 4 SAM calls per view (2×2 tiles of a 930 px photo, each tile ~512 px).
  - Strict hold check: 1 extra SAM call, only when the hand has moved away from the object.
  - Room scan ("scan the room"): ≤ 12 Spark calls at medium effort, once per room.
  - Scan give-up: 1 Spark guess at minimal effort.
  - Which saved one (T22): ≤ 4 Spark calls (minimal, text only, 8 s) per search, only when the room map has several things the word fits.
  - v9.2: look-around (names, danger, hazards, same kind), 1 Spark call (minimal) per lock, 2 if the first fails; lock verify, 1 Spark call (minimal) per lock; which-one talk, ≤ 4 Spark calls (minimal) and 1 SAM call, only when another thing like the target is nearby; hand help, ≤ 3 Spark calls (minimal) per search, only after the hand has been gone ~11 s; describe the held thing, 1 Spark call (minimal) per unsure held-up or asked check.

  Worst case, a small object with a full scan is about 37 SAM calls, roughly $0.09.
- **Correctness first, cost later (Nils, 2026-10-29 after the v5 test, ~$1 spent so far):** limits are raised so the whole flow works end to end; revisit after it does.
  - Every hold check: 1 SAM call (both layers, not only when the hand moved away).
  - Agent (unparsed commands, several candidates): effort `medium`, up to 12 SAM calls per search (several `find_object` calls to see which options are really here).
  - Room-map guess when the object is not in the map: 1 Spark call at `medium`.
  - Still event-triggered: nothing per frame.
- Log latency and estimated cost of every API call to `logs/api_calls.csv`. Reuse fixed test images in `spike/images/`.
- Coding agents: if Muse Code spend exceeds ~$15 in a day, move work back to Claude.

## Conventions
- Swift 5.9+, SwiftUI, async/await. No third-party dependencies without asking.
- API key from a gitignored `Secrets.xcconfig` / `.env`. Never commit keys.
- Small commits, message format: `area: what changed` (e.g. `guidance: add distance tones`).
- Every user-facing string is spoken: short, plain, danger first, say "not sure" instead of guessing.
- Label every file on its first line (`<!-- labels: ... -->`, `# labels: ...`, `// labels: ...`) and keep `docs/FILE_LABELS.md` in sync. New agent-written code starts as `needs-review`.
- Never delete files unless Nils says so; mark them `obsolete` instead.
- Don't guess Meta API request shapes: check https://dev.meta.ai/docs and record the working request in `docs/api-notes.md`.

## Recorded failures stay fixed (Nils, 2026-11-03: "I don't want to keep facing an issue that was captured in the log")
- Every device failure in `docs/TEST_LOG.md` that code can prevent gets an automated check in the same change: a unit test named after the run (`t17TheOtherCandidateIsCheckedBeforeScanning`), a simulator scenario, or a `tools/check_log.py` signature. "iOS build" alone is not a check. Search rules live in `FindRules` (core, tested), not only in the app's `FindModel`.
- Before every device test: `sh tools/regress.sh` (all unit tests; simulator positives 20/20, faults 0/20, no silence, no loops). After it: `sh tools/regress.sh <find_log.csv> <api_calls.csv>`; each hit is a recorded failure seen again.

## Out of scope (do not build)
Walking navigation, outdoor use, external sensors, accounts, multi-language, offline mode, medical advice. Targets beyond hand reach (Nils, 2026-11-03, after T15: from the bed, a bottle 2.9 m away got hand guidance; for the hackathon, test and demo within hand reach, no more far-target changes). The room scan need not turn a full circle: a wall behind the user has nothing to save.
